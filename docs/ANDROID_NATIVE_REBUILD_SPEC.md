# Android 原生重构技术规范（强制执行）

- 版本：1.0
- 基准界面：`桌面运维_星球主题版261113_v6.html`
- 目标：真正完成 Kotlin 原生 Android 应用，不以 WebView 套壳，不以“能编译”代替功能完成。
- 适用范围：本仓库全部后续 Android 原生框架、UI、交互、媒体导入/播放、数据迁移和 APK 构建工作。
- 执行原则：**先框架，后 UI，后功能联调与测试，最后 APK。任何阶段未通过验收，不得跳到下一阶段。**

## 0. 当前问题与纠正原则

此前版本存在以下未被充分验证的问题：
1. APK 虽然能够编译，但用户反馈界面修改后仍与原版几乎相同，说明没有完成逐页、逐组件的 HTML→原生 UI 对照验收。
2. 视频文件选择/导入无法正常完成。仅有文件选择器回调、创建课程记录或成功编译，均不能证明媒体已被正确读取和播放。
3. README 曾将部分能力描述为“已实现/一致”，但没有提供完整的设备端验收证据。

因此，后续不得以局部补丁、静态检查、成功构建或代码存在作为功能验收。所有状态必须区分：未实现、实现中、代码检查通过、模拟/自动测试通过、真机验证通过。

## 1. 不可违反的总要求

1. 原 HTML 是界面、交互、文案、主题、布局和动效的唯一基准。除用户明确批准外，不擅自改变页面信息架构、视觉语言或业务逻辑。
2. Android 必须使用 Kotlin 原生 View / AndroidX 组件实现。不得使用 WebView 承载原 HTML，不得以 HTML 页面伪装原生应用。
3. 保留原有业务数据和学习逻辑；重构时通过明确接口适配，不得为了迁移方便删除功能、隐藏入口或替换成空壳。
4. 页面控件必须有真实动作。禁止“看起来可点但无回调”、假按钮、无结果的菜单项和占位空页面。
5. 不允许把本地文件“上传到服务器”作为导入方案。课程媒体应由 Android Storage Access Framework（SAF）读取，默认本机处理；界面必须准确表达“选择/导入/复制到应用内”，不得误称上传。
6. 所有文件读写、目录扫描、媒体元数据探测、媒体复制均在后台执行；UI 线程只负责状态展示和交互。
7. 文件权限、URI 生命周期、异常、取消、重复导入、零文件、超大文件、文件被移动/删除等边界均需处理。
8. 未完成阶段验收不得构建 APK。禁止为了验证小改动频繁构建 APK。

## 2. 阶段门禁与交付顺序

### Phase A — 原生代码框架（先完成）

本阶段只建立架构、模块边界、接口契约、依赖和可测试骨架；不以大规模 UI 美化作为本阶段目标。

必须建立以下层次：

| 层 | 职责 | 禁止事项 |
|---|---|---|
| app / application | Application、依赖组装、生命周期 | 不直接承载业务逻辑 |
| navigation | 页面路由、返回栈、Tab、深链/恢复 | 页面间互相强制引用内部 View |
| design-system | DesignTokens、主题、间距、字体、图标、动效规范 | 页面散落硬编码颜色/尺寸 |
| ui / screens | 每个业务页面及其状态展示 | 不直接执行大文件 IO |
| ui / components | 可复用卡片、列表、按钮、弹层、空状态 | 不复制多套近似组件 |
| domain | 用例、模型、业务规则、校验 | 不依赖 Android View |
| data | Repository、持久化、导入导出、映射 | 不由 UI 直接拼 JSON/文件路径 |
| platform / storage | SAF、URI 授权、文件访问、媒体解码适配 | 不假定所有 URI 都是文件路径 |
| playback | 播放会话、播放队列、进度、错误与释放 | 不在页面中散落播放器生命周期代码 |

框架交付文件至少包括：
- `docs/ANDROID_NATIVE_REBUILD_SPEC.md`（本文件）
- `docs/HTML_TO_NATIVE_PAGE_MATRIX.md`（逐页映射与验收矩阵）
- `docs/MEDIA_IMPORT_PLAYBACK_SPEC.md`（媒体导入与播放契约）
- `docs/ARCHITECTURE.md`（模块依赖图、数据流、生命周期）
- 可编译的包结构、接口、模型与依赖声明。

Phase A 验收：
- 所有页面和入口都有唯一 screen / route 标识。
- 页面导航、返回栈、Tab 切换与页面状态恢复有统一实现。
- UI、domain、data、platform 分层依赖方向清楚；domain 不依赖 Android UI。
- 媒体导入、媒体播放、存档导入导出分别有接口与错误模型。
- 数据模型和本地持久化有版本迁移策略。
- 自动检查通过；不得存在为了占位而宣称功能可用的空实现。
- 形成架构图、页面清单、接口清单和测试计划，用户可审阅。

### Phase B — UI 逐页重建（框架验收后）

以 HTML 页面为基准逐项实现：
- 页面骨架、顶栏、底栏、导航层级、安全区和滚动区域。
- 星球版/极简版、明暗主题、主题色、颜色派生、字体层级。
- 卡片层级、留白、圆角、阴影、图标、标签、空状态。
- 弹层、菜单、搜索、编辑器、导入页、课程页、播放器页。
- 点击、长按、拖动、横滑、选中反馈、弹入/淡入/页面切换动效。
- 适配窄屏、常见 Android 屏幕密度、横竖屏、系统字体缩放与系统栏。

必须创建 `docs/HTML_TO_NATIVE_PAGE_MATRIX.md`，每个页面至少记录：
HTML 对应入口/选择器、原始结构、原生 screen、组件拆分、交互清单、状态来源、完成状态、截图对照证据。
UI 验收需按页面逐一对照，不接受只检查首页或只看整体“差不多”。

Phase B 验收：
- 所有 HTML 页面/弹层/状态均有对应实现或明确记录为不适用并说明理由。
- 主要屏幕尺寸截图对照完成；布局、颜色、层级、文案、入口无明显错位/缺失。
- 每个可交互元素均有可追踪的 action 和结果。
- 用户确认 UI 方向后才能进入最终功能联调。

### Phase C — 功能与数据联调

所有功能必须由 UI → ViewModel/UseCase → Repository → Platform/Storage 贯通。
必须覆盖课程创建/编辑/删除、文字导入、媒体导入、学习记录、划线、搜索、导出/导入、主题设置、TTS、播放和进度恢复。
必须提供单元测试/仪器测试或可重复的自动化验证；不可自动化的设备步骤必须提供清晰真机验收清单。

### Phase D — APK 构建（最后）

仅当 Phase A、B、C 全部通过才可执行：
1. clean build。
2. Kotlin 编译、资源检查、Lint、单元测试、仪器测试（可用时）。
3. APK 安装启动检查、关键路径冒烟测试。
4. 生成 APK 和完整源代码 ZIP。
5. 发布构建日志、版本号、提交 SHA、产物大小和未覆盖测试说明。

APK 构建不得被视为真机全功能测试。没有实体设备执行的项目必须明确标注“未真机验证”。

## 3. 媒体导入与播放：硬性技术契约

### 3.1 文件导入语义

- 文件夹导入：使用 SAF `ACTION_OPEN_DOCUMENT_TREE`，获取并持久化 READ 授权；只有在确实需要写入时才申请 WRITE。
- 单文件/多文件导入：使用 `ACTION_OPEN_DOCUMENT` / `OpenMultipleDocuments`，读取返回的 content URI，并持久化 READ 授权。
- 不允许将 `content://` URI 当作普通文件路径。所有访问必须通过 ContentResolver 或受控的应用内副本。
- 不能只按扩展名过滤。应结合 MIME、DisplayName 和实际可打开性判断；不支持的文件须明确告知。
- 扫描必须递归且有深度、文件数量、取消和超时/异常边界；每个目录查询失败应记录原因，不得静默返回“没有文件”。
- 导入结果须报告：发现数、支持数、成功登记数、无法读取数、跳过数及原因。
- 重复导入须有可预测的去重策略，排序必须稳定自然排序。
- 用户取消选择不应创建空课程或破坏已有课程。
- 媒体文件不上传网络。复制到应用内部存储是可选策略；即使不复制，只要 URI 授权有效也应能播放。

### 3.2 媒体数据模型

每个媒体章节至少保存：
- stable media ID、课程 ID、章节 ID
- display name、MIME、size、lastModified
- 原始 content URI（不可假设永久有效）
- 持久化授权状态/来源树 URI
- 应用内副本路径（若已复制）
- duration、thumbnail/poster、probe status
- import status、last error、checksum（适用时）

### 3.3 媒体导入状态机

至少包含：
`Idle → Picking → PermissionGranted → Scanning → Reviewing → Importing → Ready`
以及 `Cancelled`、`PartialSuccess`、`Failed`。
每一步必须可显示真实状态；失败必须保留可重试动作和具体错误，不可只弹“导入失败”。

### 3.4 播放器

- 采用独立 PlaybackController/Repository 管理播放器实例；UI 只订阅播放状态。
- 评估并采用 AndroidX Media3 ExoPlayer 作为统一音视频引擎；明确媒体格式/设备解码限制，不承诺所有编码都可播放。
- 支持 content URI 和应用内副本两种来源。
- 处理准备中播放/暂停、seek、倍速、完成后重播、错误恢复、音频焦点、耳机拔出、页面离开、Activity 重建、资源释放。
- 进度按稳定 media ID 持久化；不得因切换章节将旧进度写入新章节。
- 媒体播放计入学习计时的规则必须有单元测试。
- 不实现后台播放，除非产品要求明确提出；但必须定义页面/Activity 生命周期暂停策略。

### 3.5 媒体验收用例

至少测试：
1. 从常见本地文件管理器选择一个 MP4。
2. 从系统文件选择器多选 MP4。
3. 选择含多层子文件夹的目录，正确扫描全部支持文件。
4. 选择 MP3/M4A/WAV 等音频。
5. 用户取消、拒绝授权、URI 失效、文件删除、0 字节文件、同名文件。
6. 大文件复制中断后重试，不留下可误认为完整的文件。
7. 导入后立即播放、暂停、拖动进度、切换章节、完成后重播。
8. 关闭并重开应用，验证授权和进度恢复。
9. 不复制到应用内时，验证原 URI 仍可播放；失效时显示重新连接入口。
10. 不支持的编码/容器提供明确错误说明。

### 3.6 对当前实现的已知风险（先调查，不盲目补丁）

- 当前 `MainActivity` 使用 `OpenMultipleDocuments`，但 UI 反馈“改选单个文件”；命名/交互需统一。
- 当前 `MediaCourses.fromUris` 主要按扩展名筛选；需要覆盖无扩展名但 MIME 正确的文件。
- 当前 `pickTree` 只尝试持久化 READ 权限；需验证系统返回 flags、异常与授权恢复。
- 当前扫描函数虽支持深度限制，但需验证递归顺序、取消、目录查询错误和性能。
- 当前创建课程后媒体 URI 是否仍可访问尚无端到端测试证据。
- 当前复制功能是可选本地副本流程，不能将“课程记录创建成功”当作“媒体文件已上传/复制成功”。
- 当前播放器代码需检查对 SAF URI、编码兼容、生命周期和错误状态的完整覆盖。
以上是调查清单，不允许在未明确问题根因前继续打零散补丁。

## 4. 开发工作方式

每次开发按以下格式记录：
- 当前阶段与阶段目标
- 本次实际修改的文件和责任边界
- 与 HTML 基准的对应项
- 自动检查结果（具体命令/任务）
- 真机测试状态（通过/未执行/失败）
- 未解决问题与阻塞项
- 是否允许进入下一阶段

每个功能先写验收标准，再实现，再测试。若无法证明原生代码能满足要求，先停下来报告技术限制和替代方案，不做无效改动。

## 5. 当前仓库的执行状态

在本规范写入时：
- 原始 HTML 文件已在仓库根目录。
- 当前工程已有 Kotlin 原生 Activity、Page、Store、SAF 与播放器实现，但没有经过本规范要求的架构门禁和逐页 UI 对照验收。
- 用户反馈当前 APK 视觉变化不明显，视频文件无法正常导入；这些反馈视为未解决缺陷。
- 当前 APK/源码包的成功构建不代表上述缺陷已修复。
- **下一步只能先完成 Phase A 框架审计与重构方案；不得立即再次构建 APK。**

## 6. 完成定义

只有同时满足以下条件，才可对用户宣称“重构完成”：
- Phase A 架构门禁通过。
- Phase B 每页 UI 对照门禁通过。
- Phase C 所有核心功能验收通过，媒体用例全部完成。
- Phase D 构建、安装启动和冒烟测试完成。
- 源码 ZIP 与 APK 均交付，并清楚说明未覆盖的设备/格式限制。
